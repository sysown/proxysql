## Source concerns, separate from policy approval

**C1 — X connection reuse does not establish transaction/session/prepared ownership.** At END a response terminal unconditionally calls return_backend_to_pool. The reuse predicate excludes in_transaction/has_prepared_statement, but the only production call to set_in_transaction is false during reset: SQL transaction commands and SESSION_STATE_CHANGED/SESSION_VARIABLE_CHANGED payloads are not interpreted into tracked transaction/sql_mode state. The cache matches only hostgroup/frontend user/schema/TLS and reset() clears local buffers/flags rather than executing a backend SQL/session reset. Thus correct reuse for BEGIN, SET sql_mode/user variables and other backend-local state is not established. PREPARE_PREPARE sets its pin only if backend_conn_ already exists at dispatch; after a lazy connect it can set that flag, but the next terminal destroys the nonreusable connection instead of retaining it for the owning frontend. A prepared handle/cursor sequence therefore cannot be assumed to retain its backend. Successful Session::Reset marks the backend noncacheable and destroys it, yet consumes its OK without forwarding an OK to the frontend. These are source-level failure/state concerns, not reproduced runtime outcomes or options to approve unsafe sharing. I-4–I-7's session principles must be checked against this optional MySQL protocol extension rather than inferred from a predicate name. ## Decisions about surviving externally visible policies

### EX01 — MySQLX opt-in identities, local authentication and lazy backend admission

**Before:** Immediately before the May 1 chassis integration there was no in-tree MySQLX plugin or X listener. Ordinary mysql_users did not grant access through an X endpoint. This is a new optional protocol surface, not replacement of the core MySQL protocol.

**After, surviving END:** The terminating X path joins active frontend runtime_mysql_users with active mysqlx_users; a missing row on either side excludes the identity. It implements MYSQL41 and TLS-only PLAIN, validates locally using a native *HEX40 verifier or a cleartext-derived SHA1 verifier, resolves the user default_route before AuthenticateOk, and connects/authenticates to a backend on the first request. mapped is the backend-auth default; separate backend credentials can be supplied. backend_auth_mode=pass_through round-trips as configuration but authentication explicitly refuses it. The July integration repaired stock MYSQL41 payload formats and mapped-password fallback.

**Operator/client consequence:** A successful frontend login proves local credential and route resolution, not backend connectivity or backend authentication. Operators must load the core identity and then the X identity snapshot; the X endpoint needs an actual X-capable backend, normally port 33060, rather than a classic-protocol 3306 service.

**Activation / tier / default:** Plugin Chassis build with mysqlx selected and active bound routes; no default X routes are seeded. MYSQL41 can run without TLS unless user.require_tls is set; allowed_auth_methods empty permits either wired method.

**Decision:** Is the supported terminating-X admission contract local opt-in authentication followed by backend authentication on first use, with reserved backend pass_through rejected: **yes or no**?

### EX02 — MySQLX backend encryption follows the frontend by default

**Before:** In the immediately preceding integrated X implementation, backend TLS was implicitly driven by frontend encryption and endpoint use_ssl. The May 3 integration introduced explicit disabled/preferred/required/as_client selection while keeping as_client as the default.

**After, surviving END:** The actual backend consumer computes its posture from mysqlx-tls_backend_mode, endpoint use_ssl and frontend encryption before pool lookup. as_client requests TLS only for a TLS frontend; required requests it even for a plaintext frontend. preferred permits a parsed backend TLS-capability error 5001 to fall back to plaintext authentication; other/malformed errors fail. Requested TLS without a worker SSL context fails in the session path. The cache distinguishes negotiated TLS state. This describes encryption selection, not a verified hostname/trust policy; see C2/C3 below.

**Operator/client consequence:** A plaintext MYSQL41 frontend can cause a plaintext backend leg under the default. Encrypting only the client leg is not a declaration that all possible backend connections are always encrypted.

**Activation / tier / default:** Plugin Chassis/mysqlx; default backend mode as_client. Explicit preferred is best effort. Endpoint override and frontend-control discrepancies are recorded as concerns rather than offered for approval.

**Decision:** Should the backend default be **A: as_client, retaining plaintext for a plaintext frontend unless endpoint use_ssl requests TLS**, or **B: required for every backend leg**?

### EX03 — MySQLX TLS passthrough changes the identity and inspection boundary

**Before:** The preceding May 1 X implementation terminated TLS at ProxySQL. A passthrough enum/prototype was not an operational end-to-end transport; it did not establish backend-controlled authentication.

**After, surviving END:** The May 3 implementation resolves a backend from the listener route before local identity authentication when CapabilitiesSet(tls=true) reaches a passthrough route. It relays that capability request and the backend acknowledgement, then forwards opaque bytes through a dedicated nonreusable backend connection. Local mysqlx_users validation, SQL inspection, message compression processing and per-request pool sharing no longer apply inside that encrypted stream. Without the TLS upgrade, the ordinary local-auth path remains reachable; the route label alone is not a mandatory-upgrade check (C2).

**Operator/client consequence:** Once upgraded, backend credentials and backend TLS identity become the client trust boundary; the proxy cannot enforce plaintext SQL/user policy within the connection. This differs from the unsupported backend_auth_mode=pass_through on the terminating path.

**Activation / tier / default:** Plugin Chassis/mysqlx, explicit mysqlx_routes.tls_mode=passthrough and client TLS upgrade; route default inherit keeps termination.

**Decision:** For an explicitly upgraded passthrough route, is dedicated opaque forwarding with backend-owned authentication and no local X identity/SQL enforcement the supported contract: **yes or no**?

### EX04 — MySQLX compression is negotiated at the proxy and bounded independently of the backend

**Before:** Before May 1 there was no X listener. The initial integrated X plugin already advertised and implemented zstd_stream/lz4_message; it is incorrect to describe May 3 as first adding compression merely because a parity document still says compression is rejected.

**After, surviving END:** The terminating frontend advertises both algorithms, starts uncompressed, validates the selected capability, decompresses inbound payloads before normal X dispatch, and compresses forwarded outbound messages. A decompressed message is capped at 16 MiB. Unsupported/malformed negotiation uses 5052; an unnegotiated Compression uses 5170; decompression errors use 5171. Small messages and failed outbound compression can be emitted uncompressed. The backend handshake does not negotiate a matching compressed leg.

**Operator/client consequence:** Client compression does not reduce all proxy-to-backend traffic or grant arbitrary expansion sizes. Drivers must accept a valid mixture of compressed and uncompressed server messages. The error-code followups refine compatibility, rather than establishing new SQL semantics.

**Activation / tier / default:** Plugin Chassis/mysqlx terminating path, explicit client capability negotiation; no compression until negotiated. Opaque TLS passthrough delegates message behavior to the backend.

**Decision:** Is proxy-terminated frontend compression, with a 16 MiB expansion cap and uncompressed-message fallback, the supported compatibility boundary: **yes or no**?

### EX06 — DuckDB reuses application credentials for a shared embedded database

**Before:** The September 6 integration added DuckDB as a new optional plugin. Neither the baseline nor the preceding mainline tree had a DuckDB server module to migrate; existing SQLite3 and ClickHouse paths were separate facilities.

**After, surviving END:** The plugin opens one embedded DuckDB engine and creates independent MySQL/PostgreSQL listeners. Each connection owns a DuckDB connection to that same engine, while frontend authentication uses the core PROXYSQL_SESSION_SQLITE credential path (mysql_users or pgsql_users). There is no DuckDB-specific per-user schema/table authorization layer in the execution callback. Defaults are writable :memory:, 1GB memory limit, two engine threads, 100 combined admission reservations, and 0.0.0.0 listeners on 6031/6034.

**Operator/client consequence:** An application credential that can authenticate on an exposed plugin listener can execute DuckDB SQL against shared analytical contents. PostgreSQL/MySQL database names do not select isolated engine instances. Default data is process-lifetime memory, not automatically a durable database.
