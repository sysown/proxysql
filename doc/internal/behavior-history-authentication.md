### AU04 — The pass-through TLS requirement applies to cache misses (resolved)

**Integration:** [`e9dfbeb21`](https://github.com/sysown/proxysql/commit/e9dfbeb21dd7225d0cc123b57651b489a05258c0). **Activation/tier/default:** MySQL PROXYSQL31/40 pass-through; require_tls=true by default. Independently configured row use_ssl/require_x509 requirements still apply.

**Before:** No pass-through learning path or pass-through TLS setting existed.

**After at END:** The username allowlist and applicable row certificate policy run before lookup, but require_tls is tested only after a cache miss. A cached credential can satisfy caching_sha2 fast authentication without frontend TLS when no other account policy requires it. RSA support does not override require_tls for a cold probe; turning require_tls off permits the protected RSA full-auth path when available.

**Observable effect:** A cold non-TLS login fails under require_tls=true; after another client warms that username over TLS, a non-TLS client knowing the same password can authenticate locally. The variable currently protects credential acquisition, rather than every session using learned credentials.

**Recorded decision:** The non-bot Behavior section of [Rene-authored PR #6028](https://github.com/sysown/proxysql/pull/6028) explicitly preserves the miss-only pass-through TLS check: it runs after cache lookup and before acquiring cleartext credentials/backend probing. This is already specified behavior, not an unanswered policy choice.

**Evidence:** [preceding lib/MySQL_Protocol.cpp](https://github.com/sysown/proxysql/blob/71df1e0e853d1d96bed23b78413da97576ce5df5/lib/MySQL_Protocol.cpp#L2395); [lib/MySQL_Protocol.cpp:3561](https://github.com/sysown/proxysql/blob/9516441f7bd6fdb93f255f1881db19ca9ee56778/lib/MySQL_Protocol.cpp#L3561); [lib/MySQL_Protocol.cpp:3652](https://github.com/sysown/proxysql/blob/9516441f7bd6fdb93f255f1881db19ca9ee56778/lib/MySQL_Protocol.cpp#L3652); [lib/MySQL_Protocol.cpp:3424](https://github.com/sysown/proxysql/blob/9516441f7bd6fdb93f255f1881db19ca9ee56778/lib/MySQL_Protocol.cpp#L3424).

### AU06 — A trusted client certificate is an additional account condition (resolved)

**Integration:** [`0a7a023a2`](https://github.com/sysown/proxysql/commit/0a7a023a2a219900daebcd40aababbe1cc232d6f). **Activation/tier/default:** MySQL PROXYSQL31/40. require_x509 absent/false leaves ordinary certificate-optional authentication; true opts in. SPIFFE remains a separate name/URI identity policy.

**Before:** SPIFFE SAN matching already existed, but a generic require_x509 account attribute was not enforced.

**After at END:** require_x509=true requires the physical frontend connection to be TLS, to present a certificate, and to have X509_V_OK verification evidence, in addition to its password/plugin exchange. It does not bind certificate subject/SAN to the username. Nonboolean require_x509 denies authentication. The condition is checked for initial login, row-backed pass-through and a COM_CHANGE_USER target; unknown-user pass-through has no per-user attribute.

**Observable effect:** A client holding any certificate trusted by the proxy CA can satisfy this factor for another account whose password it knows. Operators needing a named identity must separately configure SPIFFE. Forwarded PROXY-protocol identity is not certificate evidence.

**Recorded decision:** The non-bot Behavior section of [Rene-authored PR #6028](https://github.com/sysown/proxysql/pull/6028) explicitly defines require_x509=true as additive to ordinary password/plugin authentication and requiring frontend TLS, a presented peer certificate and X509_V_OK. It also fixes enforcement against the original physical connection evidence for COM_CHANGE_USER. No additional subject/SAN-to-username binding is part of this condition; SPIFFE supplies its separate identity policy. This is already specified behavior, not an unanswered policy choice.

**Evidence:** [preceding lib/MySQL_Protocol.cpp](https://github.com/sysown/proxysql/blob/ea06281684809619c8e6db40819de23201685404/lib/MySQL_Protocol.cpp#L3581); [lib/MySQL_Protocol.cpp:132](https://github.com/sysown/proxysql/blob/9516441f7bd6fdb93f255f1881db19ca9ee56778/lib/MySQL_Protocol.cpp#L132); [lib/MySQL_Protocol.cpp:182](https://github.com/sysown/proxysql/blob/9516441f7bd6fdb93f255f1881db19ca9ee56778/lib/MySQL_Protocol.cpp#L182); [lib/MySQL_Protocol.cpp:3426](https://github.com/sysown/proxysql/blob/9516441f7bd6fdb93f255f1881db19ca9ee56778/lib/MySQL_Protocol.cpp#L3426).

### AU01 — Enabling pass-through changes existing empty-password accounts

**Integration:** [`e9dfbeb21`](https://github.com/sysown/proxysql/commit/e9dfbeb21dd7225d0cc123b57651b489a05258c0). **Activation/tier/default:** MySQL frontend; effective only on PROXYSQL31/40. Master enabled=false; empty_password=true; unknown_users=false. Stable commit forcibly turns the master gate off.

**Before:** An existing mysql_users row with password='' could accept a passwordless login through ordinary authentication. No backend credential-learning probe existed.

**After at END:** Enabling the master switch plus its default empty-password sub-gate changes those rows into pass-through signals. The client must use caching_sha2_password and supply a nonempty credential for a fresh backend probe; native-password passwordless login is rejected. A configured SPIFFE identity remains an identity policy and is excluded from this interpretation. Pass-through COM_CHANGE_USER is refused.

**Observable effect:** An operator enabling the feature to add some externally authenticated users also changes every eligible existing empty-password account; a legacy native-password health check can stop logging in.

**Question:** Should the master pass-through switch reinterpret all existing empty-password rows by default? **A:** Yes, with empty_password=true as now. **B:** Require explicit per-account pass-through intent in addition to the master switch.

### AU02 — Unknown-user admission synthesizes account policy

**Integration:** [`e9dfbeb21`](https://github.com/sysown/proxysql/commit/e9dfbeb21dd7225d0cc123b57651b489a05258c0). **Activation/tier/default:** MySQL PROXYSQL31/40; master=false and unknown_users=false. Username pattern defaults empty (allow all); default_hg=0; schema override empty.

**Before:** An application username absent from the runtime frontend store failed local authentication unless the separate LDAP path supplied it.

**After at END:** With both gates enabled, a matching unknown username can authenticate against a fresh backend selected from passthrough_default_hg. No mysql_users row is created. Each frontend derives current global HG/schema defaults; schema_locked=false, transaction_persistent=true, fast_forward=none and max_connections=0. **Observable effect:** A valid database account can enter through the proxy without an admin-provisioned row and without a per-user proxy connection quota. Changing the global pass-through HG affects its next frontend connection even when its credential remains cached.

**Question:** What should authorize unknown-user pass-through admission? **A:** The two global gates, with an optional username allowlist and synthesized policy. **B:** Require a nonempty allowlist and an explicit default account-policy template. **C:** Require a provisioned frontend account for every admitted username.

### AU03 — Learned credentials become a username-wide authentication authority

**Integration:** [`e9dfbeb21`](https://github.com/sysown/proxysql/commit/e9dfbeb21dd7225d0cc123b57651b489a05258c0). **Activation/tier/default:** MySQL PROXYSQL31/40 pass-through opt-in. cache_ttl_s=0 means no age expiry. Cache is process memory, keyed by username; hostgroup_probed is metadata, not part of lookup.

**Before:** There was no independently learned pass-through credential cache. An absent/empty configured credential did not become a reusable locally verified secret after a backend login.

**After at END:** After one successful fresh backend probe, the cleartext is cached and subsequent frontend logins verify locally. TTL is measured from insertion, not extended by hits. No ordinary USERS load automatically clears this cache; explicit flush/evict commands, positive TTL expiry or a later marked session's backend 1045 can evict it. That eviction is independent of connection retry budget. A wrong cached-password attempt does not itself evict/reprobe.

**Observable effect:** After a database password rotation, the old password can continue to pass frontend authentication until expiry/flush or a new backend authentication rejection. A login can remain available while no backend is reachable; the first real query may still fail. This consequence follows from the source paths, not a live outage test.

**Question:** How long should a successful backend probe authorize later frontend logins? **A:** Username-wide cached authority until the configured eviction conditions, with zero TTL allowed. **B:** Require a finite lifetime and revalidation on expiry. **C:** Revalidate each frontend login against a backend.

**Evidence:** [preceding lib/MySQL_Protocol.cpp](https://github.com/sysown/proxysql/blob/71df1e0e853d1d96bed23b78413da97576ce5df5/lib/MySQL_Protocol.cpp#L2395); [lib/MySQL_Passthrough_Auth_Cache.cpp:62](https://github.com/sysown/proxysql/blob/9516441f7bd6fdb93f255f1881db19ca9ee56778/lib/MySQL_Passthrough_Auth_Cache.cpp#L62); [lib/MySQL_Passthrough_Auth_Cache.cpp:137](https://github.com/sysown/proxysql/blob/9516441f7bd6fdb93f255f1881db19ca9ee56778/lib/MySQL_Passthrough_Auth_Cache.cpp#L137); [lib/MySQL_Session.cpp:2469](https://github.com/sysown/proxysql/blob/9516441f7bd6fdb93f255f1881db19ca9ee56778/lib/MySQL_Session.cpp#L2469); [lib/MySQL_Session.cpp:4554](https://github.com/sysown/proxysql/blob/9516441f7bd6fdb93f255f1881db19ca9ee56778/lib/MySQL_Session.cpp#L4554); [lib/Admin_Handler.cpp:1074](https://github.com/sysown/proxysql/blob/9516441f7bd6fdb93f255f1881db19ca9ee56778/lib/Admin_Handler.cpp#L1074).

### AU05 — Probe failure classification controls lockout and login availability

**Integration:** [`e9dfbeb21`](https://github.com/sysown/proxysql/commit/e9dfbeb21dd7225d0cc123b57651b489a05258c0). **Activation/tier/default:** MySQL PROXYSQL31/40 pass-through. Defaults: 3 credential failures/user, 10/source IP in 60 s; 100 concurrent probes; 100000 failure-map keys. These gates apply to cache-miss probes, not all ordinary authentication.

**Before:** No pass-through probe rate limits, shared in-flight probe budget or failure-map eviction policy existed.

**After at END:** A cache miss requires a fresh backend connection rather than a username-only pooled success. No healthy backend/pool slot fails the login immediately; pass-through does not retry the probe. Only backend errors 1045/1698/1130 add lockout failures; transport/other errors do not. Lockout attempts do not prolong the sliding window. User/IP gates reject generically; capped failure maps can evict older keys. The probe success returns its backend to the pool and then completes frontend admission.

**Observable effect:** A brief backend outage can reject a cold login while an already cached account still authenticates. An IP shared by many users shares the IP budget, while backend password-expiry error 1862 is classified outside the credential-lockout set.

**Question:** Is this the intended pass-through failure contract? **A:** Fresh fail-fast probe, generic login failure, and lockout only for 1045/1698/1130. **B:** Retry transient probe failures within a separately configured login budget, retaining credential-only lockout accounting. **C:** Make failure classification and retry budget operator-configurable.

**Evidence:** [preceding lib/MySQL_Session.cpp](https://github.com/sysown/proxysql/blob/71df1e0e853d1d96bed23b78413da97576ce5df5/lib/MySQL_Session.cpp#L2928); [lib/MySQL_Session.cpp:2608](https://github.com/sysown/proxysql/blob/9516441f7bd6fdb93f255f1881db19ca9ee56778/lib/MySQL_Session.cpp#L2608); [lib/MySQL_Session.cpp:2651](https://github.com/sysown/proxysql/blob/9516441f7bd6fdb93f255f1881db19ca9ee56778/lib/MySQL_Session.cpp#L2651); [lib/MySQL_Session.cpp:4497](https://github.com/sysown/proxysql/blob/9516441f7bd6fdb93f255f1881db19ca9ee56778/lib/MySQL_Session.cpp#L4497); [lib/MySQL_Passthrough_Auth_Cache.cpp:361](https://github.com/sysown/proxysql/blob/9516441f7bd6fdb93f255f1881db19ca9ee56778/lib/MySQL_Passthrough_Auth_Cache.cpp#L361).

### AU07 — RSA key configuration failures preserve or substitute a serving identity

**Integration:** [`6a6913b7b`](https://github.com/sysown/proxysql/commit/6a6913b7b5ad8d7f325a61530c129114bc1cacd7). **Activation/tier/default:** MySQL PROXYSQL31/40. Basic RSA feature/default ON/persistent RSA2048 is explicitly decided in #5988; this question concerns its failure policy only.

**Before:** Non-TLS caching_sha2 full authentication could not use a ProxySQL RSA key. No RSA key-configuration reload or startup fallback existed.

**After at END:** A failed runtime key reload retains the last accepted key snapshot and restores accepted variable values while other variable work can continue. During initial loading, an invalid nondefault pair triggers an attempt to load/generate the compiled default pair; if that also fails, RSA is disabled and TLS authentication remains available. A partial existing pair is never overwritten. An exchange pins its key from the full-auth challenge, including client-pinned-key mode added by #6032, so in-progress exchanges survive rotation.

**Observable effect:** A mistyped configured key path at startup can cause the endpoint to serve its default identity instead; pinned clients then fail even though the proxy starts. A failed rotation can leave the old key serving until a valid reload.

**Question:** What should happen when the configured RSA key pair is unusable? **A:** Retain the last accepted pair; on first load try defaults, then continue TLS-only. **B:** Retain the last accepted pair; on first load disable RSA without substituting defaults. **C:** Treat an explicitly configured unusable pair as a startup error.

### AU08 — PostgreSQL authentication_method becomes a minimum-strength floor

**Integration:** [`5940f34ca`](https://github.com/sysown/proxysql/commit/5940f34cacca6342fe644b4e5f71e4284bcf0775). **Activation/tier/default:** PostgreSQL frontend, all tiers. Default remains SCRAM (3); selectable floor range 1..3. Hash/verifier storage is opt-in through the password field.

**Before:** The configured method directly selected the frontend challenge; the credential was generally treated as plaintext, including for MD5 calculation/backend password handoff.

**After at END:** Stored SCRAM verifier always selects SCRAM, even under an MD5/cleartext floor. A stored md5 secret selects MD5 under floor 1/2 and is generically refused under floor 3. Plaintext follows the configured floor. A malformed SCRAM-SHA-256$ verifier is skipped at load rather than interpreted as literal plaintext; recognized hash-looking passwords become reserved formats.

**Observable effect:** Lowering the global method no longer guarantees that every client sees that method. A legacy MD5-only driver cannot authenticate a verifier-stored account merely because the operator lowers the floor.

**Question:** Should the global method be a minimum floor reconciled with auto-detected secret formats? **A:** Yes, with the implemented plaintext/md5/SCRAM matrix. **B:** Keep the configured wire method authoritative and require explicit account-level format/method configuration.

**Evidence:** [preceding lib/PgSQL_Protocol.cpp](https://github.com/sysown/proxysql/blob/c31006d844ec789551fb6cca84317c3dfc254d9d/lib/PgSQL_Protocol.cpp#L402); [lib/PgSQL_Protocol.cpp:395](https://github.com/sysown/proxysql/blob/9516441f7bd6fdb93f255f1881db19ca9ee56778/lib/PgSQL_Protocol.cpp#L395); [lib/PgSQL_Authentication.cpp:119](https://github.com/sysown/proxysql/blob/9516441f7bd6fdb93f255f1881db19ca9ee56778/lib/PgSQL_Authentication.cpp#L119); [lib/PgSQL_Thread.cpp:1045](https://github.com/sysown/proxysql/blob/9516441f7bd6fdb93f255f1881db19ca9ee56778/lib/PgSQL_Thread.cpp#L1045).

### AU09 — Weak PostgreSQL floors retain a challenge-method existence signal

**Integration:** [`5940f34ca`](https://github.com/sysown/proxysql/commit/5940f34cacca6342fe644b4e5f71e4284bcf0775). **Activation/tier/default:** PostgreSQL all tiers; only mixed secret types with authentication_method=1/2. Default SCRAM floor avoids this particular difference.

**Before:** The challenge followed the same configured method for known and unknown users; unknown users could later receive an explicit User not found response. There was no uniform mock-failure contract.

**After at END:** Unknown/too-weak credentials run mock exchanges and return generic authentication failure. However, an unknown user receives the floor's challenge while a known stronger-format user can receive a different challenge before any password. #6373 removes the distinct empty-password error and makes comparisons constant-time, but explicitly retains this method-selection limitation.
