## Questions about surviving externally visible policies

### AD01 — Conflicting core listener configuration aborts the whole startup

**Before:** Phase 3 started protocol listeners without a cross-module overlap preflight; bind failures were encountered by individual listener paths.

**After, surviving END:** A preflight compares Admin MySQL/PostgreSQL/Telnet/Stats listeners with the MySQL and PostgreSQL traffic listeners. A detected conflict logs the configuration error and calls `exit(EXIT_SUCCESS)` before plugin init/start and traffic admission. One-shot plugin early actions execute before this preflight and can exit successfully even if normal listeners conflict.

**Operator/client effect:** A configuration with an overlap on one protocol prevents the other protocol from starting, rather than yielding whichever listeners can bind. An offline bootstrap operation can still proceed. A launcher observing only the exit status sees successful termination even though the configuration was rejected.

**Activation / tier / default:** All tiers; automatic whenever the configured core listener sets overlap. It is not a check of every feature-plugin listener.

**Decision:** For a detected cross-module core listener overlap, should ProxySQL **A: abort the whole startup with exit status 0 as now**, **B: abort with a nonzero exit status**, or **C: continue only the safely bindable modules**?

### AD02 — REST route file grammar and row identity

**Before:** The text file reader recognized only `restapi`, and skipped a route lacking an explicit `id`; export wrote `restapi`.

**After, surviving END:** The reader prefers `restapi_routes` when both sections exist, otherwise accepts `restapi`. Export writes `restapi_routes`. An omitted ID uses SQLite-generated identity; timeout must be 100..100000000 and the row is skipped otherwise. `interval_ms` is tried before `timeout_ms`.

**Operator/client effect:** A file containing both sections silently selects one dataset. ID-free route definitions can load, but scripts depending on stable numerical route IDs need explicit IDs. The timeout alias has a defined precedence.

**Activation / tier / default:** All tiers when `LOAD RESTAPI ... FROM CONFIG` or the config-import path reads routes; REST API activation remains separately configured.

**Decision:** Is this grammar the compatibility contract: prefer `restapi_routes`, retain `restapi` as fallback, permit generated IDs, and prefer `interval_ms` if both timeout spellings are present: **yes or no**?

**Operator/client effect:** A plugin's successful publish result can leave its intended route or user absent while servers and other rows were applied. A caller must inspect collisions, not only the success flag. This is a specific collision policy, not arbitrary partial failure of core LOAD.

**Activation / tier / default:** PROXYSQL40 scoped publisher; no operator switch. Identity includes MySQL backend/frontend user variants, not just a username string.

**Decision:** For colliding users/rules, should publication **A: succeed with skipped rows and an explicit collision list**, or **B: reject the whole scoped plan**?

### AD12 — Managed deployment installation moves into ordinary startup

**Before:** The first integrated managed startup path accepted a local manifest via `--aws-managed-bootstrap`, forced foreground/no angel retry for that one-shot operation, applied through the management service and exited. Without a manifest it called restore.

**After, surviving END:** The bootstrap CLI and the one-shot exit branch are removed. With aws_managed enabled the normal startup path binds the management service and calls its restore callback with no manifest pointer; the provider owns automatic installation from launch inputs or recovery from durable state.

**Operator/client effect:** An operator cannot use the former core CLI to separate managed installation from starting service. The normal managed launch must supply enough provider state/inputs for installation or recovery. Core ordinary disk/bootstrap loading still runs earlier, so the service restore can subsequently replace its managed scope.

**Activation / tier / default:** PROXYSQL40 only; top-level `aws_managed` defaults false and requires a boolean, exactly one ABI15 service provider, and the web v1 binder. Detailed AWS provider payload/authentication policy is outside this stream.

**Decision:** Is automatic provider installation/recovery as part of the ordinary managed launch the intended product workflow, replacing the core manifest one-shot CLI: **yes or no**?

### AD13 — Managed apply failure can follow already visible changes to earlier families

**Before:** There was no core mapped managed-runtime API spanning users, servers, rules, variables and TLS material.

**After, surviving END:** The prepared managed runtime is validated separately, but activation writes TLS files and editable tables, loads servers, users and rules, then applies variables and their projections in sequence. An error at a later stage returns a stage-specific failure after earlier stages may already have changed state; no encompassing restoration is present in this activation routine.

**Operator/client effect:** A `VariablesApplyFailed` response does not establish that the previous servers/users/rules/TLS configuration remains active. A management provider needs a recovery/retry policy capable of reconciling desired and applied revisions. The separate scoped MySQL publisher has different rollback machinery (AD10/AD11).

**Activation / tier / default:** PROXYSQL40 callers of managed-runtime activation, both engine mappings; no global cross-family atomicity is already promised by I-1..I-8. The provider's durable-operation handling must be examined separately.

**Decision:** Should managed activation promise **A: partial changes may be visible on failure and must be reconciled**, or **B: failure preserves the preceding configuration across all mapped families**?

### AD14 — Discovery reconciliation preserves observed role and status by default

**Before:** No chassis discovery desired-set merge existed alongside ordinary configured server installation.

**After, surviving END:** The merge replaces membership within delegated hostgroups while preserving rows outside that delegation. For an endpoint already in the runtime snapshot, it keeps the current hostgroup placement and status unless any desired row for that endpoint requests force_topology_role; other desired attributes are refreshed. Endpoints omitted from the desired set disappear from the delegated slice.

**Operator/client effect:** A refresh of discovery configuration does not automatically return a monitor-moved or shunned endpoint to the hostgroup/status requested by the provider. A forced-role submission can deliberately reassert desired placement. Ordinary core LOAD remains an unconditional installation under I-1.

**Activation / tier / default:** PROXYSQL40, installed discovery controller and accepted desired sets; applies to MySQL and PostgreSQL. Default merge has no force flag set by core.

**Decision:** For an already present endpoint, should discovery **A: preserve observed placement/status unless the provider explicitly forces topology**, or **B: make every desired-set submission authoritative for placement/status**?

### AD15 — Discovery updates may persist only their delegated server slice

**Before:** The chassis did not expose discovery desired sets with selectable MEMORY/DISK materialization; ordinary server SAVE operated on its configured family.

**After, surviving END:** A desired set selects runtime_only, memory, or memory_and_disk. After the runtime reconciliation, materialization saves only the delegated hostgroups into editable rows, and optionally copies only that slice to DISK. runtime_only leaves editable/durable configuration alone. The queued acceptance result is not proof of completed application; completion carries the applied outcome.

**Operator/client effect:** Discovered endpoints can survive restart without a separate global operator SAVE when the provider requests disk persistence, while unrelated hostgroups retain their operator configuration. A runtime-only discovery membership can disappear after restart or a fresh config LOAD.

**Activation / tier / default:** PROXYSQL40, accepted desired sets in either protocol; persistence is a field chosen by the controller, not a new global SAVE default. The queue is bounded and failures/completions must be consumed by the provider.

**Decision:** Should controller submissions be permitted to select **A: runtime only / MEMORY / MEMORY+DISK per delegated slice**, or **B: runtime only with persistence reserved for explicit operator SAVE**?

## Corrections, restorations and historically superseded machinery

These are evidence categories, not questions requesting permission to restore correct behavior:

- **Dual-protocol lifecycle and wire replies:** STOP/START now includes PostgreSQL; PAUSE/RESUME avoid duplicate replies and reject invalid repeated states. Later Admin resultset dispatch selects the actual session protocol, repairing PostgreSQL crashes in runtime/Cluster queries. The revised paths survive END at `Admin_Handler.cpp` command dispatch and `admin_send_resultset`.
- **Configuration fidelity:** bound/escaped values and single-prefix normalization repair text import; fast-routing/firewall/hostgroup/TLS exports no longer omit supported data. The ordinary config database versus text-file precedence was not newly reversed by these fixes. SQLiteServer variable import was an omitted path restored in March.
- **Schema upgrades and persistence:** server status/checksum column ordering and explicit inserts were repaired; canonicalizing CREATE TABLE avoids destructive rebuild on a cosmetic prefix difference. Chassis ownership, secret and generation ledgers reject unknown destructive rebuilds; known ownership-ledger v1 migration preserves rows inside a transaction. This source establishes recovery mechanics, not a promise that every arbitrary older/custom schema is supported.
- **Safe lifetime and teardown:** Admin clients are drained before owner destruction, workers/idle threads leave their loops before object deletion, plugin callback exceptions are contained, and web requests drain while their provider and core dependencies remain alive. These close unsafe shutdown paths; they do not need a maintainer choice to permit use-after-free.
- **Core/extension separation:** early integrated GenAI/MCP core ownership is superseded by the plugin carve-out. ABI-14 server-module table transport/preparation was removed by the October followups; END retains a rejecting ABI slot rather than an active server-module facility. Do not ask maintainers to approve a mechanism that no longer exists at END.
- **Stable restoration:** TSDB and later chassis startup/Cluster/shutdown hooks were gated out of Stable. The fact that an intervening integration changed Stable does not authorize retaining the change; I-2 applies.

Correction evidence is preserved in the immutable integration links in the coverage ledger below. Relevant END owners: [configuration reader](https://github.com/sysown/proxysql/blob/9516441f7bd6fdb93f255f1881db19ca9ee56778/lib/ProxySQL_Config.cpp#L152), [safe schema materialization](https://github.com/sysown/proxysql/blob/9516441f7bd6fdb93f255f1881db19ca9ee56778/lib/ProxySQL_Admin.cpp#L3687), [retired server-module registration](https://github.com/sysown/proxysql/blob/9516441f7bd6fdb93f255f1881db19ca9ee56778/lib/ProxySQL_PluginManager.cpp#L413), [provider drain](https://github.com/sysown/proxysql/blob/9516441f7bd6fdb93f255f1881db19ca9ee56778/lib/ProxySQL_PluginManager.cpp#L1276), [phase-4 shutdown](https://github.com/sysown/proxysql/blob/9516441f7bd6fdb93f255f1881db19ca9ee56778/src/main.cpp#L2018).
