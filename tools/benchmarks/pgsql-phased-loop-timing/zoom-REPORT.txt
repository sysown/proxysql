Each candidate uses20s warmup and a50s continuous workload. perf stat tracepoint counters are attached after5s with events initially disabled, then explicitly enabled/disabled with acknowledged FIFO controls for a30s steady window. Count all syscall entries in the target proxy process plus named I/O, poll and connection entries; separately count ret==-11 exit events to identify EAGAIN. Exit counters are not added to total syscall entries. All event running percentages are100%: no event multiplex scaling. No ptrace/strace stop-resume instrumentation is used.

Query-counter snapshots bracket the perf control interval. ProxySQL's pool Queries counter counts backend query submissions; its completion delta can differ by at most the outstanding requests in this closed-loop workload. PgBouncer uses networkbench total_query_count. Snapshot and event-enable timing differ slightly; both raw ratios and timing metadata are preserved. Reported calls/query are approximate, with the timing alignment span under1%of the30s window; this is not a strict statistical error bound. read/write counters include all descriptors in the proxy process, not an fd-filtered frontend/backend breakdown. Counter tracing can perturb execution, so diagnostic TPS is not a throughput comparison.

PgBouncer makes about4read calls and2write calls per query, plus0.047epoll_wait calls; about6total syscalls/query. On this Linux, libc recv/send appear as recvfrom/sendto syscalls. ProxySQL has49recvfrom EAGAIN returns in the traced window (0.000091/query); the tracked PgBouncer EAGAIN counters are zero. This does not explain the extra PgBouncer read calls as failed reads. Read sizes/TLS record boundaries were not measured, so their cause is not established here.

Conclusion: syscall quantity alone does not explain ProxySQL's lower throughput in the earlier matched benchmark; PgBouncer issues more calls/query in this diagnostic. This measurement does not prove equal per-call costs, equal bytes copied, or equal TLS work. The timer breakdown identifies dispatch/response work as the dominant groups but does not distinguish their nested functions.

All three diagnostic workloads completed with zero failed transactions. Original PgBouncer config and prior clean inline-only ProxySQL TLS runtime were restored, no pgbench remains, and no additional configurations were tested.
